## 1. Project Overview

### What this project is

We built a machine learning system that looks at a patient's health information and estimates how likely it is that the patient has breast cancer. The estimate comes out as a probability (for example, 0.84 meaning 84%), and the system then labels the patient as **High Risk** or **Low Risk**.

On top of the model we built a simple web dashboard. A user can type in one patient's details and get an answer immediately, or upload a spreadsheet with many patients and get answers for all of them at once.

### What the system does, step by step

1. It reads 19 pieces of information about a patient (age, BMI, family history, mammogram result, and so on).
2. It converts that information into numbers the model can use.
3. The trained model produces a probability between 0 and 1.
4. If the probability is above our decision cut-off, the patient is flagged **High Risk**.
5. The dashboard shows the probability, the risk label, and the three features the model relies on most.

### What the system does NOT do

- It does not diagnose cancer. A diagnosis requires a biopsy performed by a doctor.
- It does not decide treatment.
- It does not replace any part of clinical judgement.

It is a **triage and prioritisation aid**: something that helps a clinic decide who to look at first.

### Headline numbers (measured on data the model had never seen)

| Metric | Value |
|---|---|
| Recall (malignant cases correctly caught) | **99.22%** |
| Precision (of those flagged, how many were truly malignant) | **97.96%** |
| Accuracy | **99.45%** |
| F1 Score | **98.59%** |
| ROC-AUC | **0.9982** |

Out of 387 truly malignant patients in the unseen test set, the model caught **384** and missed **3**. Out of 1,613 truly benign patients, it wrongly flagged **8**.

These numbers are unusually high. Section 26 explains honestly why, and it is the single most important thing to understand before presenting this project.

## 2. Problem Statement

### The real-world problem

Breast cancer is common. Screening programmes generate far more patients than specialists can examine carefully in a short time. A radiology or oncology department may have hundreds of files waiting. Most of those patients do not have cancer. A small number do, and for them, waiting matters.

The practical problem is therefore not "who has cancer" — only a biopsy can answer that. The practical problem is **"whose file should a specialist open first?"**

### The problem we solve

Given routinely collected patient information — demographics, lifestyle, family history, a mammogram reading, tumour measurement, and basic vitals — produce a ranked risk estimate so that high-risk patients rise to the top of the queue.

### Why machine learning is a reasonable tool for this

A human reading a single file weighs a few obvious signals. A model can weigh all 19 signals at once, consistently, for every patient, in milliseconds, and it never gets tired at 6 pm. It also produces a *number*, which means files can be sorted. A human's gut feeling cannot be sorted.

### What "success" means for us

We deliberately chose **not** to optimise for overall accuracy. In screening, the two mistakes are not equal:

- Flagging a healthy patient as high risk costs an extra test and some anxiety.
- Missing a patient who actually has cancer can cost a life.

So our target was: **catch as many malignant cases as possible, while keeping false alarms low enough that the tool is still usable.** We wrote this target down before training, in `config/config.yaml` — a minimum recall of 0.90 and a minimum precision of 0.70.

## 4. Complete Project Flow

Here is the whole project in one picture, in the order things actually happen.

```
   data/breast_cancer_prediction.csv          (raw file: 10,000 patients, 23 columns)
                  |
                  |  drop 3 columns that would give the answer away
                  v
   data/breast_cancer_cleaned.csv             (10,000 patients, 20 columns)
                  |
                  |  notebooks/01_eda_and_preprocessing.ipynb
                  |  -- look at the data, plot it, run statistical tests
                  |     (this notebook only LOOKS; it trains nothing)
                  v
   ------------------------------------------------------------
   src/preprocess.py  ->  prepare_data()
   ------------------------------------------------------------
     Step 1  drop excluded columns          (deterministic)
     Step 2  fill 3 categorical blanks      (deterministic, fixed defaults)
     Step 3  clip BMI to [15, 50]           (deterministic, clinical bound)
     Step 4  encode text -> numbers         (deterministic, fixed lookup tables)
     Step 5  SPLIT: 6,400 train / 1,600 validation / 2,000 test
                  |
                  |  the test set is now sealed. Nothing below touches it
                  |  until the very last step.
                  v
   ------------------------------------------------------------
   src/train.py  ->  6 experiments
   ------------------------------------------------------------
     For each of {LogisticRegression, RandomForest, XGBoost}
       x each of {class_weight, SMOTENC}:

         -> inside every fold: median impute -> scale -> [SMOTENC] -> fit
         -> pick best hyperparameters
         -> choose a decision threshold on the VALIDATION set

     Pick the single best experiment on validation performance
                  |
                  v
     models/best_model.pkl, models/best_pipeline.pkl,
     models/scaler.pkl, models/encoders.pkl
     outputs/metrics/model_comparison.json
                  |
                  v
   ------------------------------------------------------------
   src/evaluate.py  ->  ONE final pass on the sealed test set
   ------------------------------------------------------------
     Load the locked threshold (refuses to run without it)
     Score the 2,000 test patients exactly once
     Compute SHAP explanations
                  |
                  v
     outputs/metrics/final_metrics.json

                    precision_recall_curve,
                    shap_summary, shap_feature_importance}.png
                  |
                  v
   ------------------------------------------------------------
   app/app.py  ->  Streamlit dashboard
   ------------------------------------------------------------
     Loads best_model.pkl + scaler.pkl + encoders.pkl

```

## 5. Dataset

### The two files

| File | Rows | Columns | Size |
|---|---|---|---|
| `data/breast_cancer_prediction.csv` | 10,000 | 23 | 1,163,583 bytes |
| `data/breast_cancer_cleaned.csv` | 10,000 | 20 | 920,029 bytes |

Each row is one patient. There are **no duplicate rows** in either file — we checked all 10,000 rows and found zero exact duplicates.

### What "cleaned" actually means here

This is important, and it is different from what our older internal documents claimed.

The cleaned file is the raw file with exactly **three columns removed** and nothing else changed. We proved this: of the 200,000 cells the two files share, **zero** differ. Running `raw.drop(columns=['Patient_ID','Biopsy_Result','Cancer_Stage'])` reproduces the cleaned file byte-for-byte (identical SHA-256 hash).

So the cleaned file still contains all 1,500 blank cells. **Missing values are not filled in the CSV.** They are filled later, inside the modelling pipeline, and that is deliberate — Section 12 explains why.

Older documents in this repo claimed the cleaned CSV had missing values handled and outliers capped. That is **documented but not verified in implementation.**

### Missing values

Exactly **300 patients (3.00%)** have blanks, and every one of those 300 is blank in the **same five columns**:

- BMI
- Alcohol_Consumption
- Physical_Activity
- Hormone_Therapy
- Tumor_Size_cm

That is 300 × 5 = **1,500 blank cells**. The count of blanks per row takes only two values: 0 (for 9,700 patients) or 5 (for 300 patients). Nothing in between.

We also checked whether *being* missing tells you anything about cancer. It does not: patients with blanks had a 15.33% cancer rate versus 19.45% for complete patients, and a chi-square test gave p = 0.0881 — not statistically significant. So we treat missingness as random noise rather than as a signal.

### Where the data came from

**NOT VERIFIED.** There is no source file, licence, citation, or data dictionary anywhere in the repository. We cannot say who collected this data or from which hospital.

What we *can* say from measuring it: the data is almost certainly **synthetic (computer-generated)**, not real patient records. Three pieces of evidence:

1. **Uniform distributions.** Age, Blood_Pressure, Cholesterol, Exercise_Days_Per_Week and Annual_Income_USD all have kurtosis near −1.20, which is the mathematical fingerprint of a flat, uniform random distribution. Real patient ages are not uniformly spread from 20 to 84.
2. **Every integer present.** Blood_Pressure contains all 91 whole numbers from 90 to 180. Cholesterol contains all 171 whole numbers from 130 to 300. Real measurements clump.
3. **A discoverable generating rule.** We found a simple 8-condition rule that reproduces the cancer label with **99.34% accuracy** on all rows and **99.72%** on complete rows. Real biology does not follow a clean rule like that. Section 26 covers this in full.

Any older document that says this model was "trained on real breast cancer patient data" is **documented but not verified in implementation** — and the evidence points the other way.

## 6. Features

The model uses **19 patient attributes**. After encoding, these become **20 numeric columns** (Breastfeeding_History becomes two columns — Section 12 explains).

### What "feature" means

A feature is one piece of information about a patient that goes into the model — one column in the spreadsheet. The model learns how much each feature should push the prediction up or down.

### The full feature table

| Feature | Simple Meaning | Type | Used / Excluded | Reason |
|---|---|---|---|---|

| `Gender` | Female (9,277) or Male (723) | Binary | **Used** | Available; male breast cancer exists, so we keep it. Very weak signal (Cramér's V = 0.0026) |
| `BMI` | Body Mass Index, weight-for-height (11.1–44.1) | Numeric | **Used** | Known at screening; correlated with target (r = +0.209) |
| `Family_History` | Has a blood relative had breast cancer? No 6,979 / Yes 3,021 | Binary | **Used** | Asked in any intake form; strong signal (V = 0.254) |
| `Smoking` | Does the patient smoke? No 7,462 / Yes 2,538 | Binary | **Used** | Asked in any intake form; strong signal (V = 0.274) |

| `Cholesterol` | Total cholesterol (130–300) | Numeric | **Used** | Routine blood test. Pure noise (r = −0.0034) |
| `Diabetes` | Diabetic? No 8,296 / Yes 1,704 | Binary | **Used** | Routine comorbidity. Pure noise (V = 0.0036) |
| `Exercise_Days_Per_Week` | Days of exercise per week (0–7) | Numeric | **Used** | Lifestyle question. Pure noise (r = +0.0101) |
| `Annual_Income_USD` | Yearly income in dollars (15,002–149,996) | Numeric | **Used** | Kept as a socio-economic proxy. Pure noise (r = +0.0138) |
| `Breastfeeding_History` | Yes 4,514 / No 3,495 / "Not Applicable" 1,991 | Nominal (3 levels) | **Used** | Standard risk-history question. Becomes 2 columns after one-hot encoding |

| `Cancer_Stage` | No Cancer 8,067 / I 745 / II 602 / III 395 / IV 191 | Post-diagnostic | **EXCLUDED** | Also the answer. `Cancer_Stage != 'No Cancer'` equals `Cancer == 1` for all 10,000 rows |
| `Cancer` | 0 = benign, 1 = malignant | **Target** | Target | This is what we predict |

### Why we kept features that turned out to be noise

Blood_Pressure, Cholesterol, Diabetes, Exercise_Days_Per_Week, Annual_Income_USD, Alcohol_Consumption, Physical_Activity, Hormone_Therapy and Menopause_Status all showed essentially zero association with the target. We kept them anyway, for two reasons:

1. **We did not use the test set to decide.** Dropping features based on how they perform is itself a modelling decision, and it must be made from training data only. We measured these associations on train + validation (8,000 rows) and left the test set alone.
2. **Tree models handle useless features gracefully.** SHAP confirmed this: eight of the 20 columns received an importance of exactly **0.000000** from the final model. The model simply ignored them. Removing them would not change a single prediction.

We also did not remove any feature just because its importance looked medically surprising. That would be tuning the model to match our expectations instead of the data.

### Honest caveat on Tumor_Size_cm and Lymph_Node_Involvement

These two are the features a sharp judge will question, so here is the straight answer.

**The argument for keeping them:** both come from imaging (mammogram, ultrasound, MRI), and imaging happens *before* a biopsy. A radiologist can measure a lesion and note node involvement without knowing whether it is cancer. So at the moment our model would run, these numbers genuinely exist.

**The argument against:** in real clinical practice they are strongly associated with malignancy, and a model leaning on them is partly "predicting cancer from signs of cancer."

**What we did:** we tested `Lymph_Node_Involvement` for the one thing that would be disqualifying — whether it *determines* the label. It does not. Of the 1,635 patients with node involvement in train+validation, **983 (60.1%)** do not have cancer. Its Cramér's V is 0.264 and univariate AUC is 0.635. Compare that to the dropped `Biopsy_Result`, which has V = 1.000, AUC = 1.000, and **zero** counter-examples. That contrast is the test, and Lymph_Node_Involvement passes it as a risk factor, not a label proxy.

`Tumor_Size_cm` behaves the same way: correlation with the target is only +0.209, and there are malignant patients across the whole size range.

**What we would say to a judge:** "These are risk factors visible on imaging before diagnosis, and we verified they have thousands of counter-examples. If your clinical protocol says they arrive too late, we can retrain without them — the pipeline supports it, and our ablation test says the AUC would drop by about 0.034 and 0.023 respectively."

## 7. Target Variable

### What a target variable is

The target is the thing we are trying to predict — the "right answer" the model learns from. Everything else is an input.

### Our target

The column `Cancer`, stored as an integer, taking only the values 0 and 1. There are no missing values in it.

| Value | Meaning | Count | Percentage |
|---|---|---|---|
| 0 | Benign (no cancer) | 8,067 | 80.67% |
| 1 | Malignant (cancer) | 1,933 | 19.33% |

### Why this makes it a binary classification problem

Two possible answers means **binary classification**. That choice cascades through the whole project: it is why we use classification algorithms rather than regression, why our metrics are precision and recall rather than mean squared error, and why we need a decision threshold at all.

### The imbalance

For every malignant patient there are about **4.17 benign patients** (8,067 ÷ 1,933 = 4.1733). This is called **class imbalance**, and it is the single most consequential property of this dataset. Section 13 explains how we dealt with it.

You can see that exact number inside the trained model: XGBoost's `scale_pos_weight` is set to **4.173807599029911**, computed from the training split.

## 8. Data Leakage

### What data leakage means

Data leakage is when information that would **not** be available at real prediction time sneaks into training. The model then scores brilliantly in testing and fails completely in production, because in production that information does not exist yet.

The classic example: predicting whether someone will default on a loan, using a column called "sent to collections." The model looks perfect. It is useless, because you only know about collections *after* the default.

We treated leakage as the number one risk in this project, and we checked five separate kinds of it.

### Kind 1 — Target proxy columns

Three columns had to go before anything else.

| Column | Used in the model? | Removed? | Why | Available at prediction time? |
|---|---|---|---|---|
| `Patient_ID` | No | **Yes, dropped** | A serial number carries no medical meaning. Its correlation with the target is −0.0068 (nothing). But an ID lets a tree model memorise individual patients instead of learning patterns | Yes — but useless, and dangerous |
| `Biopsy_Result` | No | **Yes, dropped** | This *is* the target in different words. We verified on all 10,000 rows: `(Biopsy_Result == 'Malignant').astype(int)` equals `Cancer` **exactly**. Its chi-square statistic equals n (8,000 on train+val), which is the algebraic signature of a perfectly deterministic relationship | **No.** A biopsy result only exists *after* the biopsy. If you have it, you no longer need a prediction |
| `Cancer_Stage` | No | **Yes, dropped** | Also the target restated. Verified on all 10,000 rows: `(Cancer_Stage != 'No Cancer').astype(int)` equals `Cancer` **exactly**. And the stage counts (745 + 602 + 395 + 191) sum to exactly 1,933 — the number of cancer cases | **No.** Staging happens after diagnosis |
| `Mammogram_Result` | **Yes, kept** | No | This is the screening test result — precisely the input a triage tool should use. It is the strongest legitimate signal we have (Cramér's V = 0.293, chi-square p = 4.5 × 10⁻¹⁸³). Crucially it does **not** determine the label: even "Suspicious" patients are only 37.6% malignant, so 62.4% are counter-examples | **Yes.** A mammogram is what triggers the whole workflow |
| `Lymph_Node_Involvement` | **Yes, kept** | No | Visible on pre-biopsy imaging. Verified as a risk factor, not a proxy: 983 of 1,635 positive cases (60.1%) are cancer-free, V = 0.264, AUC = 0.635, chi-square ≠ n | **Yes**, from imaging — though see the caveat in Section 6 |

The exclusion list is not buried in code. It is declared in `config/config.yaml` lines 15–18, so anyone can audit it in five seconds.

### Kind 2 — Preprocessing leakage

**What it is:** if you compute a median or a scaler's mean/standard deviation over the *whole* dataset before splitting, then your training set has secretly learned something about your test set. Every test row contributed to that median.

**What we did:** we split every transform into two categories, and this distinction is written into the docstring at the top of `src/preprocess.py`.

**Deterministic transforms — safe before the split.** These use no information from the data at all, only rules fixed in advance:
- dropping the excluded columns
- mapping "Yes"/"No" → 1/0 using a fixed dictionary
- clipping BMI to the fixed physiological range [15, 50] — a clinical bound, not a percentile of our data
- filling three categorical blanks with fixed defaults ("No", "Moderate", "No")

Give these functions the same patient row and they return the same output, no matter which other rows are present. So they leak nothing.

**Learned transforms — must be fitted on training data only.** These are statistics of the dataset:
- median imputation of the 7 numeric columns
- StandardScaler's mean and standard deviation

We implemented these as custom scikit-learn estimators (`MedianImputerDF`, `StandardScalerDF`) and put them **inside** the pipeline. That means during 5-fold cross-validation, each fold computes its own medians and its own scaler from that fold's training portion only.

**We verified this held.** The saved scaler's mean differs from the training-split mean by exactly **0.00e+00**, and the saved medians match the training-split medians exactly (Age 52.0, BMI 27.1, Tumor_Size_cm 2.5, Blood_Pressure 135.0, Cholesterol 214.0, Exercise_Days_Per_Week 4.0, Annual_Income_USD 81,572.0).

### Kind 3 — Resampling leakage

**What it is:** SMOTE creates synthetic minority-class patients. If you run it on the whole dataset before splitting, synthetic patients built from a test patient's neighbours end up in training. The model has effectively seen blurred copies of the test set.

**What we did:** SMOTENC is a step *inside* an `imblearn.Pipeline`. imblearn's pipeline applies samplers during `fit` and skips them during `predict`. So held-out folds and the validation and test sets are **never** resampled — they stay at their natural 19.3% positive rate. You can confirm this in the split statistics: positive rates are 0.1933 (train), 0.1931 (validation), 0.1935 (test). If resampling had leaked, validation and test would be near 50%.

### Kind 4 — Threshold-tuning leakage

**What it is:** the decision cut-off (0.50, 0.45, …) is a real model parameter. Choosing it by trying values on the test set and keeping whichever looked best is leakage, even though no weights changed.

**What we did:** the threshold is chosen on the **validation** set from the fixed candidate list `[0.50, 0.45, 0.40, 0.35, 0.30]`, using a rule written down in advance (`config/config.yaml` lines 124–128): *highest recall among candidates with precision ≥ 0.70, ties broken on F1*. The winner is saved into `models/encoders.pkl` as `decision_threshold`.

`src/evaluate.py` then **loads** that value. It does not recompute it. If the value is missing, the script raises an error rather than quietly falling back to 0.50. The Streamlit app reads the same key and shows a hard error if it is absent (`app/app.py` lines 299–305). One number, one source, three consumers.

Older documents claimed `evaluate.py` lowers the threshold when recall falls below 90%. It does not — it refuses to. That is **documented but not verified in implementation.**

### Kind 5 — Model selection leakage

**What it is:** trying six models on the test set and reporting the best one. The reported score is then the maximum of six noisy numbers, which is biased upward.

**What we did:** all six experiments were compared on **validation** data. XGBoost + class_weight won there. Only then was the test set opened, once, for a single scoring pass. The test set was never used for tuning, model selection, threshold selection, feature selection, SMOTE fitting, or preprocessing fitting.

Any document claiming XGBoost "won on the test set" has the order wrong — that is **documented but not verified in implementation.**

### Automated leakage verification

`verify_methodology.py` runs **23 automated checks** covering all of the above and reports **23/23 PASS** with exit code 0. It is a script anyone can run:

```bash
python verify_methodology.py
```

## 9. Exploratory Data Analysis (EDA)

### What EDA means

EDA is looking at your data before you model it — counting things, plotting distributions, checking for oddities. You do it to find problems early and to build intuition about what the model will probably rely on.

### Where our EDA lives

`notebooks/01_eda_and_preprocessing.ipynb`. It has 39 cells (22 code, 17 markdown) and ran cleanly — execution counts 1 through 22 with no gaps and zero error outputs.

**Be precise about what this notebook does:** it only *explores*. It contains no scikit-learn, no XGBoost, no `train_test_split`, no GridSearchCV, no SMOTE, and no `joblib`. It imports only numpy, pandas, matplotlib, seaborn and scipy.stats. All modelling happens in `src/`. The notebook sets `RANDOM_STATE = 42` but never actually uses it.

It also references a `02_model_training.ipynb`, which does not exist in this repository.

### What we actually looked at

| Analysis | What we found |
|---|---|
| Shape, dtypes, `describe()` | 10,000 × 23 raw; 7 integer columns, the rest float or text |
| Missing-value table | 1,500 blanks in 5 columns, all in the same 300 patients |
| **Leakage crosstabs, run BEFORE dropping** | `Biopsy_Result` and `Cancer_Stage` are perfectly diagonal against `Cancer`. This is the evidence for Section 8 |

## 10. Data Cleaning

### What data cleaning means

Fixing the data before modelling: filling blanks, handling impossible values, removing duplicates, correcting types.

### What we did, and where

The cleaning is deliberately split across two places, and understanding why is the point of this section.

| Step | Where it happens | Learned from data? | Detail |
|---|---|---|---|
| Drop 3 leakage columns | `drop_excluded_columns()`, before the split | No | Patient_ID, Biopsy_Result, Cancer_Stage |
| Fill 3 categorical blanks | `clean_deterministic()`, before the split | No — fixed defaults | Alcohol_Consumption → "No", Physical_Activity → "Moderate", Hormone_Therapy → "No" |
| Clip BMI to [15, 50] | `clean_deterministic()`, before the split | No — clinical bound | Values outside the physiological range are pulled to the edge |
| Fill numeric blanks with medians | `MedianImputerDF`, **inside the pipeline, after the split** | **Yes** | BMI and Tumor_Size_cm are the two numeric columns with blanks |
| Scale the 7 numeric columns | `StandardScalerDF`, **inside the pipeline, after the split** | **Yes** | Section 12 |
| Remove duplicates | **Not implemented** | — | Not needed: there are zero duplicate rows |

### Why the split matters — the whole point in one paragraph

A **constant** fill ("always put 'No' here") is a decision we made in advance. It cannot leak, because it does not look at the data.

A **median** is a number computed *from* the data. If you compute the median of BMI over all 10,000 patients and then split, every test patient has quietly influenced the value used to fill training rows. That is preprocessing leakage. So medians live inside the pipeline, where cross-validation refits them per fold.

This is why `data/breast_cancer_cleaned.csv` still contains all 1,500 blank cells. It is not an oversight — filling them in the CSV would mean filling them *before* the split, using statistics from the whole dataset. Leaving them blank is the leakage-safe choice.

### Duplicates

We checked for exact duplicate rows in both the raw and cleaned files: **zero** in both, and zero even when ignoring Patient_ID. `Patient_ID` is unique across all 10,000 rows (100001–110000). So no de-duplication step was needed. The EDA notebook never runs this check — we ran it separately.

### What we deliberately did NOT do

- **We did not delete outlier rows.** In screening, extreme values are often the interesting patients.
- **We did not use mode imputation for categoricals.** Older documents say we did. We used *fixed documented defaults*, which is different — a mode is a statistic of the data and would need to be learned inside the pipeline. That claim is **documented but not verified in implementation.**
- **We did not engineer any new features.** No BMI categories, no age bands, no interaction terms. The cleaned file has zero derived columns. Section 27 lists this as future work.

## 11. Train / Validation / Test Split

### What splitting means

You cannot judge a model on the data it studied — that is like grading a student on the exact questions they memorised. So you split the data: one part to learn from, and a part held back to test honestly.

### Why we used three parts, not two

Most tutorials use two (train / test). We used three, and the third one is what makes our headline numbers trustworthy.

- **Train (6,400 patients, 64%)** — the model learns its weights here.
- **Validation (1,600 patients, 16%)** — we make *decisions* here: which of the 6 experiments wins, which hyperparameters win, which decision threshold to use.
- **Test (2,000 patients, 20%)** — opened exactly once, at the very end, to produce the numbers we report.

The reason: every time you look at a set and change something based on what you saw, you burn a little of its honesty. With only train/test, all our tuning and model selection would have happened on the test set, and the reported 99.22% recall would be the best of many attempts rather than a fair estimate.

### How the split is done

`split_train_val_test()` in `src/preprocess.py` performs a two-stage split:

```
FULL (10,000)
   |
   +-- 20% -> TEST (2,000)            <- sealed immediately
   |
   +-- 80% -> DEVELOPMENT (8,000)
                 |
                 +-- 20% of dev -> VALIDATION (1,600)
                 |
                 +-- 80% of dev -> TRAIN  (6,400)
```

### Stratification

**What it means:** keeping the same proportion of malignant patients in every split.

**Why it matters:** with only 19.33% positives, a random split could easily hand one set noticeably more cancer cases than another, making the comparison unfair.

**How we did it:** `stratify=y` on both split calls (`config/config.yaml` line 78). The result:

| Split | Rows | Positive rate |
|---|---|---|
| Train | 6,400 | 0.1933 |
| Validation | 1,600 | 0.1931 |
| Test | 2,000 | 0.1935 |

All three match the overall 19.33%. We also verified there is **zero overlap** between the three sets — no patient appears twice.

### random_state = 42

**What it means:** a fixed seed for the random number generator.

**Why we used it:** so the split is identical every time anyone runs the code. Without it, you would get different splits, different metrics, and no way to reproduce a number.

**How we used it:** `random_state=42` is set in `config/config.yaml` line 4 and passed to both split calls, to `StratifiedKFold`, to SMOTENC, and to all three classifiers. The number 42 has no significance beyond being a convention.

Older documents describe an 80/20 two-way split. The code does 64/16/20. That is **documented but not verified in implementation.**

## 12. Preprocessing

### What preprocessing means

Converting raw patient information into the exact numeric shape a model expects. Text becomes numbers, blanks get filled, and numbers get put on comparable scales.

### The pipeline, in order

```
median impute  ->  scale  ->  [SMOTENC, only in 3 of 6 experiments]  ->  classifier
```

In `src/preprocess.py`, `build_pipeline()` assembles exactly this. The final saved model's pipeline steps are `['impute', 'scale', 'clf']` — no sampler, because the winning experiment used class weighting instead.

### Step A — Encoding text into numbers

Machine learning models do arithmetic. They cannot multiply the word "Yes." So every text column becomes numeric, using **fixed lookup tables** declared at the top of `src/preprocess.py`.

**Binary encoding** — 9 columns, each becomes 0 or 1:

| Column | 0 | 1 |
|---|---|---|
| Gender | Female | Male |
| Family_History | No | Yes |
| Smoking | No | Yes |
| Alcohol_Consumption | No | Yes |
| Hormone_Therapy | No | Yes |
| Menopause_Status | Pre | Post |
| Genetic_Mutation | Negative | Positive |
| Lymph_Node_Involvement | No | Yes |
| Diabetes | No | Yes |

**Ordinal encoding** — 2 columns where order carries meaning:

| Column | 0 | 1 | 2 |
|---|---|---|---|
| Physical_Activity | Low | Moderate | High |
| Mammogram_Result | Normal | Suspicious | Abnormal |

*Why ordinal rather than one-hot:* "Low → Moderate → High" is a genuine ranking, and giving the model 0/1/2 tells it that. One-hot would throw the ordering away. (See Section 9 for the honest caveat that the Mammogram_Result order does not match observed risk.)

**One-hot encoding** — 1 column with 3 unordered levels:

`Breastfeeding_History` has values "No", "Not Applicable", "Yes". Note that **"Not Applicable" is a literal text value in the data, not a blank** — 1,991 patients have it.

There is no natural order between these, so ordinal encoding would be wrong. Instead we create two new 0/1 columns:

| Original value | `Breastfeeding_History_Not Applicable` | `Breastfeeding_History_Yes` |
|---|---|---|
| No (reference) | 0 | 0 |
| Not Applicable | 1 | 0 |
| Yes | 0 | 1 |

Two columns encode three states, because "0, 0" already means "No." This is called dropping the reference level, and it avoids a redundant column.

**One subtle but important implementation detail.** We did **not** use `pd.get_dummies(drop_first=True)`. That function infers its categories from whatever rows it happens to see. If the Streamlit app scores one patient who did breastfeed, `get_dummies` would produce a single column and the model would crash on a shape mismatch. Instead we loop over an **explicit hardcoded category list** (`ONEHOT_CATEGORIES` in `src/preprocess.py`), which produces the same two columns for the training set, the test set, and a single app user, forever.

**Result:** 19 features → **20 numeric columns**, in this exact fixed order:

```
 0 Age                                    10 Tumor_Size_cm
 1 Gender                                 11 Lymph_Node_Involvement
 2 BMI                                    12 Mammogram_Result
 3 Family_History                         13 Blood_Pressure
 4 Smoking                                14 Cholesterol
 5 Alcohol_Consumption                    15 Diabetes
 6 Physical_Activity                      16 Exercise_Days_Per_Week
 7 Hormone_Therapy                        17 Annual_Income_USD
 8 Menopause_Status                        18 Breastfeeding_History_Not Applicable
 9 Genetic_Mutation                        19 Breastfeeding_History_Yes
```

### Step B — Median imputation (learned, train-only)

**What it means:** filling a blank with the middle value of that column.

**Why median and not mean:** the median is not dragged around by extreme values. If one patient has a BMI of 44, the mean shifts; the median barely moves.

**How we used it:** `MedianImputerDF` handles the 7 numeric columns. It computes medians in `fit` and reuses them in `transform`. Inside cross-validation, every fold learns its own medians from that fold's training portion only. The medians learned from our training split, and saved into `models/encoders.pkl`:

| Column | Median |
|---|---|
| Age | 52.0 |
| BMI | 27.1 |
| Tumor_Size_cm | 2.5 |
| Blood_Pressure | 135.0 |
| Cholesterol | 214.0 |
| Exercise_Days_Per_Week | 4.0 |
| Annual_Income_USD | 81,572.0 |

Note what this means: **only BMI and Tumor_Size_cm ever actually need imputing**, since they are the only numeric columns with blanks. The other five medians are stored but never used on this dataset. They exist so the app cannot crash if a user leaves a field empty.

Older documents claim the medians were computed over all patients. They were computed over the training split only, and we verified this matches exactly. The "all patients" claim is **documented but not verified in implementation.**

### Step C — Scaling (learned, train-only)

**What it means:** StandardScaler rewrites each column so its average becomes 0 and its spread becomes 1.

**Why we used it:** the raw columns live on wildly different scales. Annual_Income_USD runs to 149,996 while Exercise_Days_Per_Week maxes out at 7. Logistic Regression would treat income as roughly 20,000 times more important simply because its numbers are bigger. Scaling removes that accident.

**How we used it — and one thing to be precise about:** `StandardScalerDF` scales **only the 7 continuous columns**. The 13 binary, ordinal and one-hot columns are left exactly as they are.

That is deliberate. Those 13 columns get handed to SMOTENC as *categorical* features, and SMOTENC needs their values to stay on their real discrete levels. A scaled "Smoking" column of −0.58 / +1.72 is meaningless to SMOTENC.

Older documents state "StandardScaler converts EVERY feature." Only 7 of 20 are scaled. That is **documented but not verified in implementation.**

### Why no ColumnTransformer

The standard scikit-learn tool for "apply this to some columns" is `ColumnTransformer`. We deliberately avoided it, and the reason is written in the module docstring: `ColumnTransformer` outputs a plain numpy array and **silently reorders columns** — transformed columns first, passthrough columns after.

That would break two things at once:
1. **SMOTENC** identifies categorical features by **integer index**. Reorder the columns and index 4 no longer means Smoking.
2. **SHAP** labels attributions by column position. Reorder and every explanation is mislabelled.

So we wrote `MedianImputerDF` and `StandardScalerDF` as DataFrame-in / DataFrame-out transformers that preserve column names and order end to end. This is one of the more defensible engineering decisions in the project.

### The app applies the identical transformation

`preprocess_input()` in `app/app.py` reimplements these steps row-wise in 8 numbered steps, reading the *saved* maps, medians and scaler from `models/encoders.pkl` and `models/scaler.pkl` — not hardcoded copies.

We verified parity across all 2,000 test patients: **maximum feature difference 0.0, maximum probability difference 0.0.** The app and the training pipeline produce bit-identical results.

## 13. Class Imbalance

### What class imbalance means

One outcome is much rarer than the other. Here, 80.67% of patients are benign and only 19.33% are malignant — a ratio of **4.17 to 1**.

### Why it is a problem

A model that ignores the data completely and predicts "benign" for everyone scores **80.67% accuracy**. That sounds respectable and is medically worthless — it catches zero cancers.

Worse, the standard training objective rewards this behaviour. The model gets more total credit from being right about the 8,067 easy benign cases than from struggling with the 1,933 malignant ones. Left alone, it under-predicts the rare class.

### Two ways to fix it

**Option A — Class weighting.** Tell the algorithm that a mistake on a malignant patient hurts 4.17× more than a mistake on a benign patient. No new data is created; the *cost* of errors is rebalanced.

**Option B — SMOTENC resampling.** Manufacture synthetic minority patients until the classes are balanced. SMOTE ("Synthetic Minority Over-sampling Technique") picks a real malignant patient, finds its nearest malignant neighbours, and creates a new patient somewhere along the line between them.

### Why SMOTENC and not plain SMOTE

Plain SMOTE interpolates every column. On our data that produces nonsense: halfway between Smoking=0 and Smoking=1 is Smoking=0.5, and halfway between Mammogram_Result=0 and 2 is 1.37. No patient can be 37% smoker or have a mammogram result of 1.37.

**SMOTENC** ("NC" = Nominal and Continuous) is built for mixed data. It interpolates the continuous columns and, for categorical columns, takes the **most common value among the neighbours** — so it always lands on a real level.

We told it which columns are categorical by integer index. Those indices are `[1, 3, 4, 5, 6, 7, 8, 9, 11, 12, 15, 18, 19]` — 13 categorical + 7 continuous = 20 features. Crucially, `get_categorical_indices()` computes them **programmatically from the actual feature-name list** rather than hardcoding them, and raises a `ValueError` if the two groups do not add up to the full column count. That means the indices cannot silently drift out of sync if a column is added.

### What we actually shipped — read this carefully

**We compared the two strategies as alternatives and never stacked them.** `config/config.yaml` lines 88–95 declares exactly two mutually exclusive experiments:

```yaml
imbalance_experiments:
  - name: "class_weight"   # cost-sensitive only, no resampling
    class_weight: "balanced"
    use_smotenc: false
  - name: "smotenc"        # resampling only, no extra weighting
    class_weight: null
    use_smotenc: true
```

Stacking both would double-count the correction and push the model to over-predict cancer.

**And the winner was class weighting.** The final shipped model is XGBoost with `scale_pos_weight = 4.173807599029911` (= 6,454 ÷ 1,546 from the training split), `class_weight = None`, and **no sampler in its pipeline**.

So: **SMOTENC is implemented, was tested in 3 of 6 experiments, and is not used by the model we ship.** We say this plainly because several older documents in this repo claim SMOTE was applied to the final model. That is **documented but not verified in implementation.**

The head-to-head result, on validation data:

| Model | class_weight F1 | SMOTENC F1 | Winner |
|---|---|---|---|
| LogisticRegression | 0.7665 | 0.7533 | class_weight |
| RandomForest | 0.8652 | 0.8263 | class_weight |
| XGBoost | **0.9855** | 0.8608 | class_weight |

Class weighting won all three times, and it also trains far faster (44.2 s vs 114.9 s for XGBoost) because it does not manufacture thousands of extra rows.

### Leakage safety of the resampling

When SMOTENC *was* used, it sat **inside** the `imblearn.Pipeline`, which applies samplers during `fit` and skips them during `predict`. Held-out cross-validation folds, the validation set and the test set were never resampled. Their positive rates stayed at the natural 19.3%.

## 14. Models We Tried

We trained **3 algorithms × 2 imbalance strategies = 6 experiments**, all with proper hyperparameter tuning. Older documents say "3 models"; the truthful count is 3 algorithms across 6 tuned experiments.

### Model 1 — Logistic Regression (the baseline)

**What it is:** the simplest sensible classifier. It draws one straight boundary through the data and turns the distance from that boundary into a probability.

**Why we included it:** you need a baseline. If a complicated model cannot clearly beat a simple one, the complexity is not earning its keep. Logistic Regression is also fully interpretable — every feature has one coefficient you can read.

**How we configured it:**
- `max_iter=2000` (the default 100 does not converge on scaled data of this size)
- `class_weight='balanced'` in the weighting experiment, `None` in the SMOTENC experiment
- Grid searched over `C ∈ [0.01, 0.1, 1.0, 10.0]` — `C` controls regularisation, i.e. how much the model is penalised for large coefficients. Low C = simpler model.
- Best value found: **C = 10.0** (the least regularisation available — the model wanted maximum flexibility)

**Result:** 96.4% recall but only 65.7% precision. It catches cancers but raises far too many false alarms.

### Model 2 — Random Forest

**What it is:** hundreds of decision trees, each trained on a random subset of the rows and columns. They vote, and the majority wins.

**Why we included it:** a single decision tree memorises its training data. A forest of them, each seeing a different random slice, averages out that memorisation. Forests also capture non-linear patterns and feature interactions automatically — "high BMI matters more after age 50" is something a forest can learn but a straight line cannot.

**How we configured it:**
- Grid searched over `n_estimators ∈ [100, 200]` (how many trees), `max_depth ∈ [5, 10, 15]` (how deep each tree may grow), `min_samples_split ∈ [2, 5]` (minimum rows needed to split a node) = 12 combinations
- Best: **n_estimators=200, max_depth=15, min_samples_split=2**
- `n_jobs=-1` to use all CPU cores

**Result:** 98.71% recall, 77.02% precision. A big improvement on Logistic Regression, but still one false alarm for every four true catches. Also the slowest at prediction time — 94.8 ms per 1,000 patients.

### Model 3 — XGBoost (the winner)

**What it is:** gradient boosting. Instead of building trees independently and voting, XGBoost builds them **in sequence**, and each new tree is trained specifically to fix the mistakes the previous trees made. It is a team where each member specialises in the previous member's blind spots.

**Why we included it:** gradient boosting is the standard strong performer on tabular data — the kind of data that lives in spreadsheets, which is exactly what we have. It typically beats Random Forest on the same data because correcting errors deliberately is more efficient than averaging over random variation.

**How we configured it:**
- Grid searched over `max_depth ∈ [3, 5, 7]`, `learning_rate ∈ [0.01, 0.1]`, `n_estimators ∈ [100, 200]` = 12 combinations
- Best: **max_depth=3, learning_rate=0.1, n_estimators=200**
- In the weighting experiment: `scale_pos_weight = 4.1738` (XGBoost's version of class weighting)
- In the SMOTENC experiment: `scale_pos_weight = 1.0`, deliberately, so the two corrections are not stacked

**Interesting detail:** the winning `max_depth` is **3** — the shallowest option offered. Each tree asks at most three questions. The model achieves its accuracy through 200 simple trees, not a few complicated ones. That is a strong hint that the underlying pattern is simple, which turned out to be exactly right (Section 26).

**Result:** 99.03% recall **and** 98.08% precision on validation. It wins on every metric simultaneously.

### How hyperparameter tuning worked

**What a hyperparameter is:** a setting *you* choose before training, as opposed to a weight the model learns. Tree depth is a hyperparameter; the split points inside the tree are learned.

**How we tuned:** `GridSearchCV` with `StratifiedKFold(n_splits=5, shuffle=True, random_state=42)`. Grid search tries every combination in the grid. 5-fold cross-validation means for each combination the training data is cut into 5 parts, the model is trained on 4 and tested on 1, five times, and the results averaged. That is much more reliable than a single train/test attempt.

Across all 6 experiments that is 4 + 4 + 12 + 12 + 12 + 12 = **56 hyperparameter combinations × 5 folds = 280 model fits**.

**What we scored on — and this is a subtle but important choice.** We tuned on **`average_precision`**, not recall.

Why: if you tune directly for recall, the winning model is the one that predicts "malignant" for every single patient. That scores 100% recall and is completely useless. Recall alone is a degenerate objective. `average_precision` summarises the whole precision-recall curve in one number and does not depend on a threshold at all, so it rewards genuinely good ranking rather than a trick. We then pick the operating threshold separately, on validation data.

Older documents say `scoring='recall'` and `cv=3`. The code says `average_precision` and `cv=5` (`config/config.yaml` lines 97–101). Those claims are **documented but not verified in implementation.**

## 16. Evaluation Metrics Explained Simply

### The four building blocks

Every classification metric is built from four counts. Here they are on our actual test set of 2,000 patients:

|  | Model says **Malignant** | Model says **Benign** |
|---|---|---|
| **Actually Malignant** | **True Positive (TP) = 384**<br>Correctly caught a cancer | **False Negative (FN) = 3**<br>Missed a cancer — the dangerous error |
| **Actually Benign** | **False Positive (FP) = 8**<br>False alarm — extra test, some anxiety | **True Negative (TN) = 1,605**<br>Correctly cleared a healthy patient |

In plain words:
- **True Positive** — we said cancer, and there was cancer. Good.
- **True Negative** — we said no cancer, and there was none. Good.
- **False Positive** — we said cancer, and there was none. A false alarm. Cost: an unnecessary follow-up test and some worry.
- **False Negative** — we said no cancer, and there was cancer. **This is the error that can kill someone.** The patient goes home reassured and comes back later with advanced disease.

### The metrics

**Accuracy** = (TP + TN) / everything = (384 + 1,605) / 2,000 = **99.45%**

*What it means:* what fraction of all patients we got right.
*Why it can mislead:* predicting "benign" for everyone here would score 80.67%. Accuracy hides which kind of mistake you are making, which is the only thing that matters medically.

**Precision** = TP / (TP + FP) = 384 / 392 = **97.96%**

*What it means:* when we say "high risk", how often are we right? Answer: about 98 times out of 100.
*Why it matters:* low precision means the clinic drowns in false alarms and starts ignoring the tool.

**Recall** (also called Sensitivity) = TP / (TP + FN) = 384 / 387 = **99.22%**

*What it means:* of all the patients who really have cancer, what fraction did we catch? Answer: 384 of 387.
*Why it matters most here:* this is the metric that counts lives. See Section 17.

**F1 Score** = the harmonic mean of precision and recall = **98.59%**

*What it means:* a single number balancing the two. It is deliberately harsh — if either precision or recall is bad, F1 is bad. You cannot fake it by maxing one out.
*Why we use it:* as a tiebreaker when two models look similar.

**ROC-AUC** = **0.9982**

*What it means:* pick a random malignant patient and a random benign patient. ROC-AUC is the probability the model gives the malignant one a higher score. 0.5 = coin flip. 1.0 = perfect.
*Why it is useful:* it measures the model's **ranking ability** independently of any threshold. Change the cut-off and precision/recall shift, but ROC-AUC does not.

**Average Precision (PR-AUC)** = **0.9966**

*What it means:* the area under the precision-recall curve.
*Why we prefer it here:* on imbalanced data, ROC-AUC can look flattering because the huge number of true negatives dominates. Average precision focuses on the minority class. This is why we tuned hyperparameters on it.

**Specificity** = TN / (TN + FP) = 1,605 / 1,613 = **99.50%**

*What it means:* of the healthy patients, what fraction did we correctly clear?

**Negative Predictive Value (NPV)** = TN / (TN + FN) = 1,605 / 1,608 = **99.81%**

*What it means:* when we say "low risk", how often are we right? This is the number a patient actually cares about when told they are cleared.

### Two metrics we do NOT compute

`MODEL_METRICS_AUDIT.md` mentions **Matthews Correlation Coefficient (MCC)** and **Log Loss**. Neither appears anywhere in the code, and neither is in `outputs/metrics/final_metrics.json`. Those are **NOT VERIFIED** as computed. If a judge asks about MCC, the honest answer is "we did not compute it, though it would be a reasonable addition for imbalanced data."

### Confusion matrix

Yes, we produce one: `outputs/plots/confusion_matrix.png`, generated by `src/evaluate.py` from the single test-set pass. The four numbers in it are the TP/TN/FP/FN above.

We also produce `outputs/plots/roc_curve.png` and `outputs/plots/precision_recall_curve.png`.

## 17. Why Recall Is Important Here

### The asymmetry of errors

This is the single most important idea in the whole project.

In most machine learning problems, the two kinds of mistakes cost roughly the same, so you optimise accuracy and move on. In cancer screening they are wildly different:

| Mistake | What happens next | Cost |
|---|---|---|
| **False Positive** — flag a healthy patient | Extra imaging or a biopsy. It comes back clear. The patient was worried for a week. | Money, clinic time, temporary anxiety. **Recoverable.** |
| **False Negative** — miss a real cancer | The patient is told they are low risk. They stop worrying. They come back months or years later with more advanced disease. | **Potentially irreversible.** |

A false positive costs a test. A false negative can cost a life. They are not interchangeable, and a metric that treats them as interchangeable — like accuracy — is the wrong metric.

**Recall is the metric that counts false negatives.** Recall = 99.22% is another way of saying "we missed 3 of 387 cancers."

### How this shaped every decision in the project

This was not a preference we mentioned at the end. It drove the architecture:

1. **We wrote the target down first.** `config/config.yaml` line 116: `target_recall: 0.90`. Set before training, not chosen after seeing results.
2. **We handled class imbalance** specifically so the model would not take the easy route of predicting "benign" for everyone.
3. **We built a threshold-selection rule that maximises recall**, subject to precision staying above 0.70: *"highest recall among candidates with precision ≥ min_precision; ties broken on F1"* (`config/config.yaml` line 128).
4. **We did not tune on recall directly**, because that degenerates into predicting all-positive. We tuned on average precision and then chose the operating point separately. This is the sophisticated version of "prioritise recall."

### Why we still care about precision

Recall alone is not enough. A tool that flags 80% of all patients as high risk would have near-perfect recall and would be thrown out within a week — the specialists would stop reading its output. Precision is what makes the tool *credible enough to be used*, and a tool nobody uses saves nobody.

Hence the floor: `MIN_PRECISION = 0.70` in `src/train.py` line 79. We will trade precision for recall, but not below 70%.

As it happens we did not need to trade at all. At threshold 0.50, XGBoost gives both 99.03% recall and 98.08% precision on validation.

### Why the threshold ended up at 0.50

Here is the validation threshold sweep for the winning model:

| Threshold | Precision | Recall | F1 | Accuracy |
|---|---|---|---|---|
| **0.50** | **0.9808** | **0.9903** | **0.9855** | **0.9944** |
| 0.45 | 0.9714 | 0.9903 | 0.9808 | 0.9925 |
| 0.40 | 0.9592 | 0.9903 | 0.9745 | 0.9900 |
| 0.35 | 0.9329 | 0.9903 | 0.9608 | 0.9844 |
| 0.30 | 0.9027 | 0.9903 | 0.9444 | 0.9775 |

Read the recall column: it is **flat at 0.9903** all the way down. Lowering the threshold catches no additional cancers — but it steadily destroys precision, from 98.08% down to 90.27%.

So the rule "highest recall, break ties on F1" picks **0.50**, because every candidate ties on recall and 0.50 has the best F1.

This is worth stating clearly to a judge: **0.50 is not a lazy default here. It is the value our written-down rule selected, and we can show the sweep that justifies it.** The three cancers the model misses at 0.50 are still missed at 0.30 — the model does not rank them near the boundary, so no threshold change rescues them.

The selected value is saved into `models/encoders.pkl` as `decision_threshold` and read by both `src/evaluate.py` and `app/app.py`.

## 18. Overfitting and How We Checked For It

### What overfitting means

Overfitting is when a model memorises its training data instead of learning general patterns. It looks brilliant on data it has seen and falls apart on anything new. The student who memorised last year's exam paper.

### What we DID implement to guard against it

**1. A sealed test set (2,000 patients, 20%).** Never used for tuning, model selection, threshold selection, feature selection, SMOTE fitting, or fitting any transformer. Opened once. This is the strongest single defence available, and it is the reason the test numbers mean anything.

**2. A separate validation set (1,600 patients, 16%).** All decisions were made here, so the test set stayed clean.

**3. 5-fold stratified cross-validation.** Every hyperparameter combination was scored as the average of 5 independent train/hold-out cycles rather than one lucky split. The result is the most useful overfitting evidence we have:

| Model | Imbalance | CV mean ± std |
|---|---|---|
| **XGBoost** | **class_weight** | **0.9969 ± 0.0030** |
| RandomForest | class_weight | 0.9882 ± 0.0041 |
| XGBoost | smotenc | 0.9848 ± 0.0044 |
| RandomForest | smotenc | 0.9620 ± 0.0059 |
| LogisticRegression | class_weight | 0.8989 ± 0.0093 |
| LogisticRegression | smotenc | 0.8794 ± 0.0122 |

The winner's standard deviation is **±0.0030**. Performance barely moved across five different data slices. A model that had memorised its training rows would swing far more than that.

**4. Regularisation built into the search.** The grids for both tree models included depth limits (`max_depth ∈ [5, 10, 15]` for the forest, `[3, 5, 7]` for XGBoost) and minimum-split sizes, which are the standard controls on tree complexity. Logistic Regression's grid searched `C`, which is a regularisation strength.

**5. The winning model chose to be simple.** XGBoost picked `max_depth=3` — the shallowest option in the grid. Each tree asks at most three questions. Overfitting models grab all the depth you offer them. This one did not.

**6. Consistency between validation and test.** Validation recall 0.9903, test recall 0.9922. Validation precision 0.9808, test precision 0.9796. The numbers barely moved on completely unseen data, which is what you want to see.

### What we did NOT implement — stated plainly

**A train-versus-test metric comparison: Not currently implemented.**

The pipeline never computes metrics on the training set. There is no `y_train_pred` anywhere, no training accuracy, no training recall. So the classic overfitting check — "training accuracy 99.9% versus test accuracy 84%, that gap is the overfitting" — cannot be shown from our outputs.

`MODEL_METRICS_AUDIT.md` contains a whole train-versus-test table with gaps between −1.37% and −3.87%, and claims a "~0.5% gap." **No training-set metric is computed anywhere in this codebase.** Those numbers are **NOT VERIFIED** and should not be quoted.

**Early stopping: Not currently implemented.** XGBoost supports `early_stopping_rounds` with a validation set. We did not use it; we fixed `n_estimators` through grid search instead.

**Learning curves: Not currently implemented.** We do not plot performance against training-set size, which would show whether more data would help.

**Explicit L1/L2 tuning for the tree models: Not currently implemented.** XGBoost's `reg_alpha` and `reg_lambda` were left at defaults.

### The honest overall conclusion

Our evidence says the model is **not overfitting in the classical sense**. The cross-validation variance is tiny, validation and test agree closely, and the winning model chose minimal depth.

But there is a bigger issue that overfitting checks cannot detect, and it is the more important one: **the dataset itself appears to follow a simple generated rule.** A model can learn that rule perfectly, generalise perfectly to other rows from the same generator, and still be useless on real patients. That is not overfitting — it is a data-provenance problem. Section 26 covers it, and it is the thing to lead with rather than hide.

## 20. Explainability

### Why explainability matters here

A doctor will not act on "the computer said 84%." They need to know *why*. And a model nobody can interrogate cannot be audited, debugged, or trusted with a clinical decision.

### What SHAP is

**SHAP** stands for SHapley Additive exPlanations. It borrows an idea from game theory: if a team wins by some margin, how much did each player contribute?

Here the "team" is the set of features and the "win" is the model's prediction. SHAP works out, for each feature, how much it pushed the prediction up or down relative to the average prediction. The values add up exactly to the difference between this prediction and the baseline — that additivity is what makes SHAP mathematically principled rather than a heuristic.

### What we implemented — and where

`src/evaluate.py` contains `compute_shap_values()`, `shap_ranking()`, `plot_shap_ranking()` and `plot_shap_beeswarm()`. These run on the **test set** during final evaluation and produce:

- `outputs/plots/shap_summary.png` — a beeswarm plot showing every test patient as a dot, so you can see both the size and the direction of each feature's effect
- `outputs/plots/shap_feature_importance.png` — a ranked bar chart
- `outputs/metrics/shap_feature_importance.csv` — the numbers

**We verified the feature labels are correct.** SHAP mislabelling is a classic silent bug: if the column order shifts anywhere, every explanation points at the wrong feature. We checked that the SHAP feature names match `estimator.feature_names_in_` exactly — 20 names, 20 values, identical order. **PASS.**

### The actual global feature ranking

Mean absolute SHAP value across the test set:

|---|---|---|
| 1 | Mammogram_Result | 2.001160 |
| 2 | Family_History | 1.860532 |
| 3 | Smoking | 1.846722 |
| 4 | Age | 1.794174 |

| 6 | Lymph_Node_Involvement | 1.701512 |
| 7 | BMI | 1.650970 |
| 8 | Genetic_Mutation | 1.327843 |

### How to read this ranking

**The cliff is the headline.** Feature 8 has an importance of 1.33; feature 9 has 0.025. That is a **53-fold drop** in one step. Eight features do all the work; eight more get **exactly zero**. The model learned to ignore them completely, without us dropping a single column. That is a genuinely satisfying result — feature selection happened automatically, and it agrees with our independent association screen from Section 9.

**Mammogram_Result being first is clinically sensible** — it is the screening test itself.

**Smoking (rank 3) above Genetic_Mutation (rank 8) is not what a doctor would expect.** In real medicine, a BRCA mutation is a far stronger risk factor than smoking. We did **not** reorder anything to make the chart look better. Here is the honest explanation, and it is a real insight:

`mean |SHAP|` mixes two different things — **how strongly** a feature affects an individual prediction, and **how many patients** it affects. Look at the numbers:

| Feature | Prevalence | Risk ratio | Cancers captured |
|---|---|---|---|
| Smoking = Yes | 25.4% of patients | 2.91× | 770 (49.8% of all cancers) |
| Genetic_Mutation = Positive | 14.5% of patients | 2.93× | 513 (33.2% of all cancers) |

Their *per-patient effect* is nearly identical (2.91 vs 2.93). But Smoking is present in almost twice as many patients, so its average contribution across the cohort is larger. Genetic_Mutation is a high-impact, low-coverage feature, and averaging dilutes it.

**A judge asking "why is smoking above genetics?" is asking a good question, and the right answer is "because mean|SHAP| averages over the whole population, and smoking is twice as common — their per-patient risk ratios are the same."** That answer demonstrates you understand your own metric.

**And SHAP shows association, not causation.** Nothing here says smoking *causes* the model's prediction to be correct, or that quitting would change a patient's outcome. It says the model uses that column.

Two completely different methods put Mammogram_Result first and rank the same eight features as the ones that matter. That agreement is worth more than either result alone.

### The important caveat about the dashboard

**`app/app.py` does not use SHAP.** This is the single most likely place for a judge to catch a misleading claim, so here it is precisely.

The dashboard shows a panel headed **"Top 3 Primary Contributing Risk Drivers"** with a column labelled **"Attribution Weight."** That reads like a per-patient explanation. It is not.

`get_top_contributing_features()` (`app/app.py` lines 253–268) reads `model.feature_importances_` — XGBoost's **global, gain-based importance**, computed once at training time. It then sorts those global importances, takes the top 3, and pairs them with *this patient's* values.

The consequence: **the app returns the same three features for every single patient.** Only the displayed values change. A 30-year-old with no risk factors and a 70-year-old with a positive genetic test get the identical three drivers.

Why this matters: global importance answers "which features does this model rely on overall?" Per-patient SHAP answers "why did *this* patient get *this* score?" They are different questions. Presenting the first as the second overstates what the dashboard does.

**What is true:** SHAP is genuinely implemented in `src/evaluate.py`, verified for correct alignment, and the plots in `outputs/plots/` are real per-patient SHAP output. It is only the *dashboard panel* that uses global importance instead.

**What is not verified:** `PRESENTATION_SCRIPT.md` claims the app can say things like "the mammogram result increased this patient's probability by 25%." No such per-patient percentage is computed anywhere in `app/app.py`. That is **NOT VERIFIED as an app capability.** Do not demo it.

**What we would say to a judge:** "The dashboard currently shows global model importance, labelled in a way that overstates it. The per-patient SHAP machinery already exists in our evaluation module — wiring `shap.TreeExplainer` into the app is a small, well-scoped change we did not make before the deadline."

## 22. Batch Prediction

### What it does

Tab 2 of the dashboard. Upload a CSV of many patients and score all of them at once. This is the feature that makes the tool operationally useful — a clinic does not want to type 400 patients in one at a time.

### How it works

1. Upload a CSV.
2. The app checks for **8 required columns** and stops with a clear error if any are missing.
3. It checks for **11 optional columns** and warns that defaults will be used for whichever are absent.
4. Every row is transformed and scored.
5. A cohort summary appears: total patients, high-risk count, low-risk count, average probability.
6. A colour-coded results table appears (red for high risk, green for low risk).
7. A download button offers the annotated CSV.

**Predictions run on all rows** — there is no row cap on the scoring itself. The displayed table is limited to the first 100 rows for readability.

### The known bug — steps 6 and 7 do not work

**This is a confirmed, reproduced, demo-breaking bug, and you must know about it before you present.**

`app/app.py` line 558 calls `.style.applymap(...)` to colour the results table. `Styler.applymap` was **deprecated in pandas 2.1 and removed in pandas 3.0**. This project's environment runs **pandas 3.0.5**.

Because that call sits inside a broad `try / except Exception` block, the failure is partial rather than obvious:

| Step | Outcome |
|---|---|
| A. Predictions computed | **Works.** We tested 50 rows: 11 high risk, 39 low risk |
| B. Cohort summary metrics rendered | **Works** |
| C. Results table rendered | **Fails** — `AttributeError: 'Styler' object has no attribute 'applymap'` |
| D. Download button rendered | **Never appears** — the exception happened before it |

What the user sees: the summary numbers, then a red error box reading *"Error during batch CSV processing: 'Styler' object has no attribute 'applymap'"*, and no table and no download.

We reproduced this end-to-end by replicating the exact code path.

**The one-line fix** is to replace `applymap` with `map` (`Styler.map` is the modern equivalent, available since pandas 2.1). We did not apply it because this documentation task explicitly prohibited modifying `app/app.py`.

**How to handle it in a demo:** either avoid Tab 2, or — better — show it, explain it in one calm sentence, and name the fix. "We're on pandas 3.0, which removed `Styler.applymap`. The predictions compute correctly; only the coloured table fails to render. It's a one-word fix to `Styler.map` that we deliberately left out of scope for this documentation pass." A judge who sees you diagnose your own bug precisely will trust everything else you say more, not less.

### What batch mode does not have

- **No authentication.** Anyone with the URL can upload patient data.
- **No file-size limit.** A 2 GB CSV would be accepted and would exhaust memory.
- **No row limit** on scoring.
- **No PII handling.** Uploaded data is processed in memory with no encryption, no audit log, and no de-identification step.
- **No input validation** beyond the required-column check.

For a hackathon prototype this is normal. For anything touching real patient data it is disqualifying, and Section 27 lists it as the first thing to build.

### Design decisions worth defending

**Configuration in YAML, not scattered in code.** The drop list, the split ratios, the hyperparameter grids, the metric targets and the threshold rule all live in one readable file. A judge can audit the leakage exclusions in five seconds without reading Python.

**The threshold has exactly one home.** Selected once on validation, written into `encoders.pkl`, read by both `evaluate.py` and `app.py`. Neither recomputes it, and both fail loudly if it is missing. Three consumers, one number.

**Custom DataFrame transformers instead of ColumnTransformer.** Preserves column names and order, which SMOTENC (integer indices) and SHAP (positional labels) both depend on. Explained fully in Section 12.

**The full pipeline goes into GridSearchCV.** Imputation, scaling and resampling are all pipeline steps, so cross-validation refits them per fold. This is what makes the CV scores honest rather than optimistic.

**Deliberate two-file dataset.** Raw and cleaned are both kept, and the cleaned file is provably just a 3-column drop, so the transformation is auditable.

**No.** We searched the entire repository for FastAPI, Flask, uvicorn, `@app.route` and `APIRouter` — **zero hits.** Streamlit is the only interface. Any claim of a REST API is **NOT VERIFIED.**

### Is it deployed?

**NOT VERIFIED.** There is no Dockerfile, no `Procfile`, no `docker-compose.yml`, no `.streamlit/` config directory, and no cloud configuration anywhere in the repository. The app runs locally via `streamlit run app/app.py`. It has never been containerised or deployed.

## 24. Business Value

### The workflow problem in numbers

Take a screening clinic that processes 1,000 patients a month. At this dataset's base rate, roughly 193 have cancer and 807 do not. A specialist reviewing files in arrival order reaches the 193 in no particular sequence — the person who needs attention most might be file number 847.

### What this tool changes

It gives every file a number, so the queue can be **sorted**. On our test set, the model ranked 384 of 387 true cancers above the threshold, while flagging only 8 healthy patients. In queue terms: a specialist working the flagged list first encounters 392 files, of which 384 are real.

That is the concrete value: **it reorders the queue.** It does not diagnose anything.

### Where the value shows up

**Prioritisation.** High-risk patients rise to the top of the review list instead of waiting their turn alphabetically.

**Consistency.** The model applies the same 19-factor weighing to every patient, every time. A human's judgement varies with fatigue, caseload and time of day. The model's does not. This is not a claim that the model is *better* than a specialist — it is a claim that it is *consistent*, which is a different and more defensible property.

**Scale.** 13.1 ms per 1,000 patients of model compute. Scoring a full month's caseload is instant. A clinic can re-score its entire waiting list whenever new information arrives.

**Auditability.** Every prediction can be traced: the exact model version, the locked threshold, the exact preprocessing, and — via SHAP in the evaluation module — which features the model relies on. That matters for clinical governance far more than raw accuracy does.

**Documentation of risk factors.** The ablation study and association screen quantify which of the 19 collected fields actually carry signal. Eight do; eleven essentially do not. That is directly useful to whoever designs the intake form.

### What we explicitly do NOT claim

We want to be precise here, because overclaiming is the fastest way to lose a technically literate judge:

- **We do not claim this replaces a doctor.** It replaces nothing. It reorders a queue.
- **We do not claim it guarantees a diagnosis.** Only a biopsy diagnoses cancer.
- **We do not claim it guarantees better patient outcomes.** Demonstrating that would require a prospective clinical trial with real patients and real follow-up. We have run no such study.
- **We do not claim any percentage reduction in mortality.** We have no evidence for any such number and will not invent one.
- **We do not claim the 99.22% recall transfers to real patients.** It was measured on 2,000 rows of what our own analysis indicates is synthetic data. Section 26.

### The honest value statement

Right now, the demonstrated value is **methodological, not clinical**.

What this project genuinely demonstrates is a leakage-safe, reproducible, auditable machine learning pipeline: three-way splitting, correct handling of learned versus deterministic transforms, resampling inside cross-validation folds, threshold selection locked before test evaluation, verified SHAP alignment, and 23 automated methodology checks. That framework is real, it is transferable, and it would be the correct starting point for a genuine clinical study.

The clinical value is **unproven**, and it will stay unproven until the same pipeline is run on documented real patient data and validated prospectively.

Saying this out loud is not a weakness in the presentation. It is the difference between a team that understands what it built and a team that read its own accuracy number and believed it.

> **This is a clinical decision-support prototype and does not replace a doctor or provide a guaranteed medical diagnosis.**

## 25. Real-World Scenario

### How this would actually be used

**Monday, 8:00 am — a screening clinic.**

Overnight, 340 patient records arrive from the weekend's screening sessions. Each has demographics, a lifestyle questionnaire, a mammogram reading, and where imaging found something, a lesion measurement and a note on lymph nodes.

**8:05 am — batch scoring.** A coordinator exports the 340 records to CSV and uploads them to the dashboard. Every row is scored. The cohort summary reports how many crossed the threshold.

**8:10 am — the sorted queue.** The coordinator downloads the annotated CSV and sorts by probability. Roughly 65 patients are flagged high risk. Based on our test-set performance, most of those flags are real and very few real cases are outside the list.

**8:30 am — the specialist starts reviewing.** She works the flagged list first. Critically, **she reviews every file herself.** The model chose the order; it did not choose the outcome. When she opens a file she sees the patient's actual data, not the model's opinion.

**During the week — individual cases.** A new patient arrives with a suspicious mammogram. The clinician enters her 19 details into Tab 1 and gets an immediate risk estimate to inform how urgently to schedule the biopsy. The estimate goes into the notes as one input among many.

**What never happens:** the model never sends a patient home. A low-risk score does not cancel a follow-up. It only affects *ordering*.

### A concrete patient walk-through

A 58-year-old woman, BMI 32, family history positive, non-smoker, genetic test negative, mammogram suspicious, lesion 3.4 cm, no lymph node involvement.

1. The dashboard encodes her: Age 58 → scaled, BMI 32 → scaled, Family_History Yes → 1, Smoking No → 0, Genetic_Mutation Negative → 0, Mammogram_Result Suspicious → 1, Tumor_Size_cm 3.4 → scaled, Lymph_Node_Involvement No → 0, plus the remaining fields.
2. All 20 columns go to the model in the exact saved order.
3. `predict_proba` returns a probability.
4. Above 0.50 → **High Risk**.
5. The clinician sees the probability, the label, and the top-3 driver panel — knowing (per Section 20) that those three drivers are the model's global preferences, not this patient's personal attribution.
6. She books the biopsy sooner rather than later. **The biopsy decides.**

### Who would use it

| User | What they get |
|---|---|
| Screening coordinator | Batch scoring to order the daily review queue |
| Radiologist / oncologist | A ranked worklist, plus a second opinion on individual cases |
| Clinic administrator | Throughput visibility — how many high-risk cases per week |
| Data scientist | An auditable pipeline to retrain on the clinic's own data |

### What would have to be true first

Before any of the above is legitimate, all of these are prerequisites:

## 26. Limitations

This is the most important section in this README. If you present this project, lead with these — do not wait to be caught.

### Limitation 1 — The dataset is almost certainly synthetic

**This is the big one.** Four independent lines of evidence:

**(a) Uniform distributions.** Age, Blood_Pressure, Cholesterol, Exercise_Days_Per_Week and Annual_Income_USD all have kurtosis around **−1.20**, the mathematical fingerprint of a flat uniform distribution. Real patient ages cluster; they are not equally likely at every value from 20 to 84.

**(b) Every integer present.** Blood_Pressure contains all 91 whole numbers from 90 to 180. Cholesterol contains all 171 from 130 to 300. Real measurements are lumpy.

**(c) Zero correlation between predictors.** The largest absolute correlation between any two of the 19 features is **0.0191**. In real medical data, BMI correlates with blood pressure, age correlates with cholesterol, and so on. Total mutual independence indicates independently sampled random columns.

**(d) A discoverable generating rule.** This is the decisive evidence. `src/investigate.py` tested a simple hypothesis on train + validation only:

> **Cancer = 1 if and only if at least 4 of these 8 conditions hold:**
> Age ≥ 50, BMI ≥ 30, Tumor_Size_cm ≥ 3.0, Family_History = Yes, Smoking = Yes, Genetic_Mutation = Positive, Lymph_Node_Involvement = Yes, Mammogram_Result ≠ Normal

That rule reproduces the label with **99.34% accuracy** on all rows and **99.72%** on complete cases. The breakdown is stark:

| Conditions met | Patients | Cancer rate |
|---|---|---|
| 0 | 429 | 0.0% |
| 1 | 1,527 | 0.0% |
| 2 | 2,390 | 0.4% |
| 3 | 2,117 | 1.0% |
| **4** | **1,072** | **97.9%** |
| 5 | 389 | 100.0% |
| 6 | 71 | 100.0% |
| 7 | 4 | 100.0% |
| 8 | 1 | 100.0% |

Look at the jump from 3 conditions (1.0%) to 4 conditions (97.9%). That is a **step function**, not a biological gradient. Real disease risk rises smoothly. This dataset has a switch.

**What this means for our results.** Our model is excellent — at learning this rule. That explains everything: why 99.45% accuracy was achievable, why the winning tree depth was only 3 (a threshold rule is simple to learn), why the signal/noise split in Section 9 was so clean, and why eight features got exactly zero SHAP importance (the rule uses exactly 8 features).

**The honest conclusion: our metrics measure how well we learned a synthetic generator, not how well we would predict real cancer.** Real breast cancer risk models achieve ROC-AUC around 0.65–0.85. Ours is 0.9982. That gap is a property of the data, not of our engineering.

**Why we are stating this rather than hiding it.** Any competent judge will notice that 99.45% accuracy on a cancer problem is impossible on real data. Getting there first — with quantified evidence — is the difference between a team that understands its results and a team that believes its own scoreboard. And the methodology we built is genuinely correct; it is only the *interpretation* of the numbers that must be qualified.

### Limitation 2 — The dashboard does not do per-patient explanations

The "Top 3 Primary Contributing Risk Drivers" panel uses **global** XGBoost gain importance, not per-patient SHAP. It returns the same three features for every patient, with only the values changing, under a label ("Attribution Weight") that suggests individual attribution. Real SHAP exists in `src/evaluate.py`, but it is not wired into the app. Full detail in Section 20.

### Limitation 3 — Batch mode is broken on pandas 3.0

`Styler.applymap` was removed in pandas 3.0; `app/app.py:558` still calls it. The predictions compute correctly and the cohort summary renders, then the results table throws and the download button never appears. Confirmed by reproducing the exact code path. One-line fix (`applymap` → `map`), deliberately out of scope for this documentation pass. Full detail in Section 22.

### Limitation 4 — No security whatsoever

No authentication, no authorisation, no file-size limit, no row limit, no input sanitisation beyond widget ranges, no PII handling, no encryption, no audit log. `unsafe_allow_html=True` is used at six places in `app/app.py`. Acceptable for a prototype; disqualifying for real patient data.

### Limitation 5 — Not deployed, and no deployment configuration

**NOT VERIFIED** — there is no Dockerfile, Procfile, docker-compose file, or `.streamlit/` directory anywhere. The app has only ever run locally.

### Limitation 6 — No API

No REST or gRPC interface. Streamlit only. A hospital system could not integrate with this as-is.

### Limitation 7 — No training-set metrics, so no classical overfitting table

The pipeline never computes metrics on the training set. Our overfitting evidence is cross-validation stability (±0.0030) and validation/test agreement, which is good evidence — but the specific train-versus-test gap table in `MODEL_METRICS_AUDIT.md` is **NOT VERIFIED** and should not be quoted.

### Limitation 8 — The Mammogram_Result ordinal order is wrong

Observed risk order is Normal (10.96%) < Abnormal (32.16%) < Suspicious (36.69%), but `config/config.yaml` encodes Normal=0, Suspicious=1, Abnormal=2. The configured order is not monotone in risk. Low impact because XGBoost splits on thresholds rather than assuming linearity, but it is a genuine defect.

### Limitation 9 — Widget ranges exceed data ranges, with no warning

Age accepts up to 90 but the data stops at 84; BMI accepts 10–60 but the data spans 11.1–44.1. Users can enter out-of-range patients and receive confident-looking predictions based on extrapolation, with no caution shown.

### Limitation 10 — No feature engineering

Zero derived features. No BMI categories, no age bands, no interaction terms, no risk composites. The model uses the 19 raw fields as given.

### Limitation 11 — No calibration check

The model outputs numbers between 0 and 1 and we call them probabilities, but we never verified that a predicted 0.7 corresponds to a 70% real-world rate. No reliability diagram, no Brier score, no Platt scaling or isotonic regression. For a tool whose output is a probability, this matters.

### Limitation 12 — Small absolute error counts

Three false negatives and eight false positives are very small numbers. Metrics computed from counts that small carry wide confidence intervals. We did not compute confidence intervals or bootstrap the test metrics.

### Limitation 13 — Single train/test split, no repeated evaluation

The test metrics come from one 2,000-row split with `random_state=42`. We did not repeat the whole procedure across multiple seeds to see how much the headline numbers move.

### Limitation 14 — Existing internal documentation is substantially stale

Three older documents in `breast-cancer-prediction/` (`DOCUMENTATION.md`, `MODEL_METRICS_AUDIT.md`, `PRESENTATION_SCRIPT.md`) predate the current training run. We audited them: **102 claims are stale or contradicted by the code, 26 are unverifiable, and 107 check out.** Notably, none of the 16 function names `DOCUMENTATION.md` documents actually exist in `src/`. Treat `outputs/metrics/*.json` and this README as the sources of truth.

### Limitation 15 — Provenance, consent and bias are undocumented

We do not know where the data came from, who consented to its use, or what population it represents. We therefore cannot assess whether the model would behave differently across ethnic groups, age bands or socio-economic strata. For a medical model this is a serious gap, not a footnote.

## 27. Future Improvements

These are concrete, scoped next steps for *this* project — things we could actually start on Monday. Not futuristic technology.

### Priority 1 — Fix the batch-mode bug

Replace `.style.applymap(...)` with `.style.map(...)` at `app/app.py:558`. One word. Restores the results table and the download button. Should be done before any demo.

### Priority 2 — Wire real SHAP into the dashboard

Load a `shap.TreeExplainer` alongside the model and compute per-patient SHAP values in `get_top_contributing_features()`. This turns the misleading global-importance panel into a genuine per-patient explanation, and it would let the app show the direction of each contribution (pushed risk up / down), not just the magnitude. The SHAP code already exists in `src/evaluate.py`; this is mostly plumbing.

### Priority 3 — Validate on real, documented data

The single highest-value improvement. Run the exact same pipeline on a real, consented, documented dataset. The pipeline is ready; the data is the missing piece. This is what would turn methodological rigour into clinical evidence. Expect the metrics to drop substantially, and treat that drop as a *success* — it would mean the numbers finally mean something.

### Priority 4 — Add authentication and basic data protection

Login, role-based access, a file-size cap on uploads, a row cap, HTTPS, an audit log of who scored which cohort when, and a documented retention policy. Non-negotiable before any real patient data touches this.

### Priority 5 — Check and fix probability calibration

Plot a reliability diagram on validation data. Compute a Brier score. If the model is miscalibrated, apply Platt scaling or isotonic regression. Right now we present raw model scores as probabilities without having verified they behave like probabilities.

### Priority 6 — Compute training-set metrics

A few lines in `src/train.py` to score the training split and report the train-versus-validation gap for every experiment. Cheap, and it closes the one overfitting-evidence gap in Section 18.

### Priority 7 — Fix the Mammogram_Result ordinal order

Change `config/config.yaml` line 35 to `["Normal", "Abnormal", "Suspicious"]` to match observed risk, and re-run. Low impact on XGBoost, meaningful for Logistic Regression, and it removes a defect a careful reviewer will find.

### Priority 8 — Warn when inputs fall outside the training range

If a user enters Age 88 (training max 84) or BMI 55 (training max 44.1), show a caution that the prediction is an extrapolation. Small change, materially more honest output.

### Priority 9 — Add confidence intervals to the reported metrics

Bootstrap the test set to put intervals around recall and precision. With only 3 false negatives, the interval on recall is wide, and reporting a bare 99.22% overstates our certainty.

### Priority 10 — Try feature engineering

Clinically motivated derived features: BMI categories (underweight / normal / overweight / obese), age bands, a count of positive risk factors, and interaction terms such as Age × Family_History. Given what we now know about the generating rule, a "count of risk conditions met" feature would likely be very strong — and testing that would be a clean way to confirm the synthetic-rule finding.

### Priority 11 — Add a REST API

A small FastAPI wrapper around the same artifacts, so a hospital information system could call the model directly instead of going through a browser. Straightforward once the artifacts are stable.

### Priority 12 — Containerise for reproducible deployment

A Dockerfile pinning Python and the 13 dependencies, plus a `.streamlit/config.toml`. Also add `scipy` to `requirements.txt` — `src/investigate.py` imports it but it is not currently listed.

### Priority 13 — Repeat the whole evaluation across several random seeds

Run the full pipeline with `random_state` in {42, 1, 7, 2024, 31337} and report the spread. Turns a single point estimate into a distribution.

### Priority 14 — Update or retire the stale internal documents

`DOCUMENTATION.md`, `MODEL_METRICS_AUDIT.md` and `PRESENTATION_SCRIPT.md` contain 102 stale claims between them. Either regenerate them from the current outputs or clearly mark them as historical.

| App shows a threshold error and stops | `decision_threshold` missing from `encoders.pkl` | Re-run `python -m src.train`. This is deliberate — the app refuses to guess a threshold |
| `ModuleNotFoundError: scipy` when running `investigate` | scipy is missing from `requirements.txt` | `pip install scipy` |
| Sidebar image does not load | The app fetches it from `img.icons8.com` | Cosmetic only; needs internet |
